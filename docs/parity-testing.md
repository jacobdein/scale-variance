# Parity testing

Two implementations, one algorithm. This document explains how we keep them aligned.

## Principle

For any valid input, the R and Python `scale_variance` and `scale_variance_raster` functions must return numerically equivalent results. "Equivalent" means:

- Identical field names and shapes in the result object.
- Floating-point fields match within `abs_tol = 1e-10, rel_tol = 1e-9`.
- Integer fields (`level`, `df`) match exactly.
- Row ordering is equivalent after sorting by `level` (or by `id` within an element table).

Drift between implementations is the single most likely bug to go unnoticed, because each package will have its own unit tests that pass in isolation. The parity suite is what catches this.

## Fixtures

Shared test data lives in `tests/fixtures/`. Each fixture is a self-contained bundle:

```
tests/fixtures/<fixture_name>/
├── meta.json              # {"kind": "tabular" | "raster", "value": "...", "id_cols": [...], "agg_fun": "mean", ...}
├── input.csv              # tabular input (kind = tabular)
├── input.tif              # raster input (kind = raster)
├── expected_components.csv    # expected `components` dataframe
├── expected_totals.json       # {"total_ss": ..., "total_df": ..., "grand_mean": ...}
└── expected_elements/
    ├── level_1.csv
    ├── level_2.csv
    └── ...
```

For raster fixtures, the `meta.json` also records `base_level_factor`, `num_levels`, and `agg_fun`. Expected outputs for raster fixtures are generated by running the canonical R reference at [`../reference/raster-R-implementation/scale-variance.R`](../reference/raster-R-implementation/scale-variance.R) — which is the behavior the v0.1 packages must replicate.

## Required fixtures for v0.1

Claude Code generates these as part of step 2 in `CLAUDE.md`. Start here; they form the acceptance gate for the first implementation.

### `fixture_mt1972_fig3` — **the gold-standard fixture**

The 16×16 checkerboard matrix from Figure 3 of Moellering & Tobler (1972). The exact values are embedded in the R reference at [`../reference/raster-R-implementation/scale-variance-example.R`](../reference/raster-R-implementation/scale-variance-example.R) Example 4.

- **Input:** 16×16 integer raster of the values 2, 5, 8 arranged in the paper's pattern. The exact matrix is embedded in the R reference at `reference/raster-R-implementation/scale-variance-example.R` Example 4 (lines ~54–72). CRS: none (or `"local"`). Extent: `(0, 16, 0, 16)`.
- **Parameters:** `base_level_factor = 2`, `num_levels = auto` (which yields 5 levels: 16×16 → 8×8 → 4×4 → 2×2 → 1×1), `agg_fun = "mean"`.
- **Expected totals (from the paper, line 156–157 of the example R file and restated in the paper's text):** `total_ss = 1152`, `total_df = 255`.
- **Expected per-level `sum_squares` and `df`.** Derive these by **both** of the following independent routes and assert they agree before committing:
  1. **Hand derivation from Moellering & Tobler Table 3** (irregular-case formulae). The checkerboard structure is regular, so the per-level SS reduces to closed-form counts of (parent_mean − child_mean)² for each scale. Write the derivation out in `fixture_mt1972_fig3/derivation.md` — show the arithmetic, not just the answers.
  2. **Running the R reference** at `reference/raster-R-implementation/scale-variance.R` on the exact Fig 3 matrix with the parameters above, capturing its `$svc` output. This is the "pragmatic" oracle.
  
  If the two routes disagree, the R reference has a bug on this input and must be investigated before the fixture is committed. If they agree, both the `expected_components.csv` and the `derivation.md` are committed together. The hand derivation is what future maintainers will audit against; the R-reference output is the pragmatic check that the paper's formulas match the paper's numbers.
- **Purpose:** direct authoritative check against the 1972 paper. No implementation gets past this.

### `fixture_even_3level_perfect`
- Synthetic 8×8 raster with 4:1 nesting to 16 level-2 cells, 4:1 to 4 level-3 cells, 4:1 to 1 level-4 cell. Values drawn from a fixed seed; no NAs.
- Purpose: validate the even-case reduction from Moellering & Tobler Table 2. Include a unit test that additionally computes the expected components from the closed-form even-case formulas and asserts equality with `scale_variance_raster` output.

### `fixture_even_with_nas`
- Same 8×8 grid as above, with 12 of the 64 level-1 cells set to `NA`.
- Purpose: validate the NA-drop + uneven-fan-out path that is the general (irregular) case the packages implement.

### `fixture_irregular_admin`
- Pure-tabular fixture (no raster). Hand-rolled small example mimicking Moellering & Tobler's motivating case (counties in states in regions). Ragged fan-out: some states have 3 counties, others have 5; some regions have 2 states, others 4.
- Exercises the `scale_variance` tabular path, not the raster path.
- Values with known grand mean, known SS per level, computed by hand and documented in `fixture_irregular_admin/derivation.md`.
- Purpose: validate the irregular case against hand-verified numbers on a non-raster hierarchy.

### `fixture_raster_mean_vs_sum`
- Small raster (16×16) with three `agg_fun` variants: `"mean"`, `"sum"`, `"modal"` (categorical). Same input raster, three meta.json variants each pointing at the same input but with different parameters.
- Purpose: exercises the `agg_fun` parameter explicitly; ensures mean and sum give the same `ss_share` proportions on a linear-scale input (they do; sum is just a scaled-up mean under aggregation) and that `modal` works on an integer-valued categorical raster.

### `fixture_landcover_binary`
- Small synthetic binary raster (32×32) simulating a land-cover class presence/absence at high resolution.
- Parameters: `base_level_factor = 2`, `agg_fun = "mean"` (yields the per-cell class proportion at each level).
- Expected generated from the raster R reference, committed alongside.
- Purpose: realistic check that the pipeline used in the NDVI + land-cover pipeline (see [`../reference/raster-R-implementation/ndvi-landcover-pipeline.R`](../reference/raster-R-implementation/ndvi-landcover-pipeline.R)) produces stable outputs across implementations.

### `fixture_base_factor_3`
- 27×27 raster (3³), `base_level_factor = 3`, three levels.
- Purpose: exercises the non-2× nesting path already parameterized in the R reference.

### `fixture_edge_single_level`
- Tabular with only one `id_cols` entry.
- Purpose: asserts the error message matches the documented text in both packages.

### `fixture_crs_unprojected_aoi`
- Spatial helper fixture. A WGS84 `aoi` GeoJSON passed to `create_hbins`.
- Purpose: asserts both R and Python `create_hbins` error with identical message text and error class (`scalevar_crs_error` / `UnprojectedCRSError`).

### Random property-based fixtures (raster + tabular)
- Five raster fixtures and five tabular fixtures, generated by deterministic seeds. Raster fixtures vary in dimension (16×16 to 128×128), `base_level_factor` (2 or 3), and NA rate (0–20%). Tabular fixtures vary in depth (2–6), fan-out (2–6, ragged), NA rate (0–20%), and row count.

**Generator.** `tests/fixtures/_generate_random.py`, invoked with a fixed master seed (`master_seed=20260424`). For each fixture:

1. Derive a per-fixture seed from the master seed.
2. Emit `input.{csv,tif}` and `meta.json`.
3. Emit `expected_*` outputs by running the **Python implementation** — which by this point has already passed the hand-derived fixtures (`fixture_mt1972_fig3`, `fixture_irregular_admin`, `fixture_even_3level_perfect`). The Python implementation is the oracle for random fixtures; R must match it.
4. The generator script is committed and deterministic. A separate CI job re-runs it and diffs against committed fixtures.

## Parity harness

A single script, `tests/run_parity.py`, orchestrates:

1. Iterates every fixture directory.
2. Determines the fixture kind from `meta.json` (tabular or raster) and dispatches to the right entry point in each package.
3. Invokes the R package via `Rscript` (with a small `parity_runner.R` in `r/inst/parity/`) to dump its result as JSON + CSVs.
4. Invokes the Python package directly, dumps its result in the same format.
5. Diffs the two against each other and against `expected_*`.
6. Exits non-zero with a readable diff on mismatch.

The harness runs in CI on every PR, matrixed over supported R / Python versions. A mismatch blocks merging.

## Unit tests inside each package

Per-package tests (`testthat` for R, `pytest` for Python) cover:

- Small hand-crafted examples with obvious answers (all values equal → all SS = 0; values perfectly separated by a single level → that level's `ss_share` ≈ 1).
- Every documented error condition — asserting the error message text.
- API ergonomics that are language-specific (NSE in R, type hints / dataclass behavior in Python; xarray vs numpy input dispatch in Python).
- Raster-specific: idempotency (`scale_variance_raster` on the same raster twice produces identical output); round-trip (wide_table from `scale_variance_raster` fed into `scale_variance` produces the same components).

These tests do *not* replace the parity suite; they catch regressions quickly in-language.

## Handling intentional deviations

If a future version introduces a deviation between R and Python (e.g. an idiom only one language supports), it must be:

1. Listed in each package's README under "Known deviations from sibling package."
2. Excluded from the parity suite via an explicit fixture annotation, not silently skipped.
3. Revisited quarterly to decide whether the other package can adopt the idiom or the deviation should be removed.

## Reconciling disagreements

When implementations disagree during v0.1 build-out, the workflow is:

1. **Re-derive the expected output by hand** (or from the paper's equations). Neither implementation is authoritative until this is done.
2. **Compare:**
   - Hand-derivation matches Python, not R → R has a bug. Fix R.
   - Hand-derivation matches R, not Python → Python has a bug. Fix Python.
   - Hand-derivation matches neither → both are wrong; back to `docs/theory.md` and the paper.
   - A separate case: if hand-derivation matches both but the **polygon R reference** disagrees (because it uses `ms_share` instead of `ss_share`), that is expected behavior — the polygon reference is historical and known to diverge from the paper on normalization. The **raster R reference** is the canonical ground truth for v0.1.
3. Never silently "reconcile" by adjusting an expected value to match either implementation's output.

When a parity failure surfaces a documented divergence between the two R references (raster vs polygon), record it in `reference/known-issues.md` with the fixture that shows it. The original code in `reference/` stays unchanged — both R references are historical artifacts preserved for traceability.
